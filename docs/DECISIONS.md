# Durable decision register

This register contains only decisions that still shape the product or its
working model. Execution chronology remains in Git history, archive tags and
issue/PR records described in [HISTORY.md](./HISTORY.md).

## Current decision status

### Product development is paused for assumption review

On 2026-09-17 the Owner paused Forme before completing R4. The implementation
history remains evidence, but the Living Project Twin, its durable judgment
model and the R1–R4 causal story are no longer treated as settled premises for
new work. Resumption requires a new explicit product decision. See
[CHECKPOINT-2026-09-17.md](./CHECKPOINT-2026-09-17.md).

### AI-generated judgment is not self-authorizing memory

Repeated model synthesis and context compaction can turn a provisional
interpretation into an apparently canonical premise while drifting from the
Owner's original meaning. Until a revised architecture is accepted, evidence,
observation, candidate interpretation, Owner judgment and working context must
not be collapsed into one automatically maintained durable judgment list.

The decisions below record the working contracts used by the first build
phase. They remain useful lineage and design evidence, not automatic authority
to continue the prior roadmap.

## Product identity

### Forme is an Owner-controlled Living Project Twin

Forme is not a generic assistant or autonomous replacement for the Owner. It
preserves continuity, improves cognition, supports bounded agency and can
represent a controlled project presence while keeping authorship legible.

### Highest Vision and MVP are one direction at different depth

The MVP must demonstrate the same constitutional shape as the Highest Vision.
It may narrow breadth and polish, but it may not replace the Living Project
Twin with a disconnected demo.

### R1–R4 form one continuity

R1 Continuity, R2 Cognition, R3 Bounded Agency and R4 Controlled Presence are
successive capabilities of one project self. Earlier accepted capabilities
must remain usable as later gates are added.

## Scope and acceptance

### P0 is the Demo-critical product flow

P0 contains only the end-to-end experience needed to prove the product
identity. P1 is admitted only after P0 is Green; P2 is outside the current
R4/R5 commitment.

### Owner experience is part of Done

Tests and technical review can make a result reviewable, but a product gate is
not Done until the Owner experiences the intended flow and accepts its
meaning and feel.

### R4 uses the Hybrid Hero Encounter

The R4 target combines a public, legible Room with an Owner-controlled Private
Room boundary. A Guest discovers a Projection, knocks, receives an
admission/decline outcome, can submit a response without server-side AI and
leaves the Owner in control.

## Agency, privacy and identity

### Human friction belongs at consequential boundaries

Routine low-risk work should remain fluid. Approval is required where an
action crosses privacy, identity, representation, spend, publication,
messaging, production or another consequential boundary.

### The server is deterministic and no-AI

Public discovery, admission state, response intake and continuation metadata
may be served deterministically. Semantic interpretation remains in the
Owner-controlled local/Harness environment unless a later explicit decision
changes that trust boundary.

### Public and private contexts do not collapse

A public Projection is intentionally bounded. It does not expose the Owner's
private workspace, private project twin or unapproved identity/context.

## Native Harness architecture

### The Native Harness is the carrier; Forme is the semantic spine

The Harness owns native workspace affordances and execution surfaces. Forme
owns project meaning, continuity, policy and durable semantic contracts.

### Native Workspace and Fresh Native Response are distinct sessions

Ordinary workspace work uses the Native Workspace Session. A Guest response
enters through a Fresh Native Response Session with explicit provenance,
bounded context and an Owner-visible handoff.

### Managed Privacy Runs are explicit effects

Actions that cross the approved human boundary use a reviewable plan,
Owner-bound approval, bounded execution and outcome/rollback evidence.

## Working model

### The clean restart separates outcome approval from engineering execution

The Owner approves user-visible outcomes, product/trust changes and real
external effects. Once an outcome boundary is clear, ordinary implementation,
tests, local synthetic work, reversible repair, evidence, commits and pull
request updates proceed autonomously. Files, hashes and attempts are not units
of Owner approval.

### Integration is not product acceptance

A reviewed fail-closed implementation may enter `main` as a development
baseline while its product issue remains open. Technical Review, integration
and Owner Experience Acceptance are separate events. Historical detail remains
recoverable through Git and tags rather than being carried in every active
task.

### GitHub is the live execution surface

During an active build phase, the active issue and integration pull request
carry mutable execution truth. Repository contracts carry stable meaning. The
Project is a concise portfolio view, not a second narrative log. During the
2026-09-17 pause, the checkpoint and cockpit replace an active issue/PR as the
live execution surface.

### Use medium-grained outcome envelopes

After the Owner approves a bounded outcome, ordinary implementation, tests,
contract-preserving repairs, evidence and local commits proceed autonomously.
Return only for a real boundary change, ambiguous effect or exhausted budget.

### Context is layered, not accumulated

The default context is a small re-entry set. Conditional contracts are opened
only when relevant. Completed chronology stays recoverable but does not remain
in active documents as repeated superseding sections.
